 PART 1   RULES
================================================================================================

 FOUR ENFORCEABLE RULES.  Each is decidable by a test over the public surface.

 R1  with_* returns an independent modified model.
     [I] Returns a new Model.  The receiver is not mutated, and the two share no mutable
         structure.  Immutable objects (strings, frozen params) may be shared.
     [V] EVIDENCE, with its limits stated.  On examples/ch3_two_player.yaml (2026-09-10), a
         reachable-object traversal to depth 14 over dicts, sequences and __dict__ finds 58
         mutable objects reachable from the model.  For all SEVEN with_* methods -- with_params,
         with_horizon, with_numerics, with_stationary, with_finite, with_signal, with_signals --
         the copy shares ZERO ids with the original.  Model.params is a mappingproxy.
     [V] Buffer sharing was checked as well, because distinct ndarray objects can share writable
         storage despite distinct ids.  It found nothing -- and the reason matters: ZERO ndarrays
         are reachable from a Model at all today.  The check is therefore VACUOUS here, not
         passed.  It becomes live the moment a model carries an array, and T1 keeps it for that.
     [V] What this does NOT establish: the contract for every model.  It is one model, one
         traversal depth, and traversal cannot see storage held behind C extension objects that
         expose no __dict__.  Two earlier drafts each generalised from a narrower check than the
         claim they stated; this note exists so the third does not.
     TEST  T1: the same traversal over SEVERAL models spanning the three horizon kinds, asserting
         an empty id intersection AND no np.shares_memory pair between reachable arrays.
         Immutable objects (strings, numbers) may be shared and are excluded.

 R2  Properties expose data.  Methods perform operations or parameterized queries.
     [I] A noun method is correct when it is a parameterized query -- kernel(name, channel),
         grid_summary().  Part of speech is not the rule and grammatical uniformity buys nothing.
     TEST  no public property takes arguments; no public method is a bare data read.

 R3  A name that reads as a predicate returns a real bool.
     [I] is_* and has_* return bool, never None.  So does any other predicate-shaped name.
         Multivalued assessments use *_status, or return a status object.
     [V] CORRECTION to draft 1: resolution_ok was cited as violating R3.  It matches neither
         is_ nor has_ -- it carries the *_ok suffix, which is a different problem.  R3 is not
         violated today; the *_ok suffix is retired under R6 instead.
     TEST  every is_*/has_* member returns bool on every engine.

 R4  require_* returns the receiver on success and raises on failure.
     [I] One-way: require_ tells you control flow may stop.  The converse is not claimed;
         validate() raises and keeps its name.
     TEST  every require_* returns self or raises; never returns a falsey value.

 R6  *_ok is retired as a suffix on ASSESSMENT PROPERTIES.
     [I] On a property reporting an assessment it reads as two-valued and is not.  Such names take
         *_status, or the assessment is read from the diagnostics object.  resolution_ok is
         removed under this rule (PART 3).
     [I] EXEMPT: require_ok().  It is a require_* METHOD governed by R4, where "ok" names what is
         being required rather than claiming a boolean return.  It returns the receiver or raises.
         Draft 2 banned the suffix outright and kept require_ok, which contradicted itself.

 ONE PRINCIPLE, NOT A RULE.

 P1  The same concept uses the same name, argument convention and type everywhere; a genuine
     difference keeps a different name.
     [I] This outranks every prefix rule and is the reason for PART 10.
     [V] CORRECTION to draft 1, which called all five rules "mechanically checkable".  This one
         is not: applying it requires deciding whether two things are the same concept, which is
         judgment.  Tests can enforce particular contracts DERIVED from it (PART 10), not the
         principle itself.

 [V] Model and Result expose 87 public members; 14 carry a prefix a rule governs (2026-09-10).
     The rules constrain names; they do not determine them.

 PART 3   DIAGNOSTICS
================================================================================================

 3.1  WHAT IS WRONG
 [V] Demonstrated 2026-09-10, one model per engine, guards on:

         stationary       converged=True  resolution=False  window=True   second_order:a=True
         finite/spectral  converged=True  resolution=True   (no window)   second_order:a=True
         finite/cells     converged=True  resolution=None   (no window)   (NO second_order row)
                          -> status ok = True

     The cell engine passes the whole verdict while running two fewer checks: one it cannot
     compute, one it does not emit.
 [V] With diagnostics=False, require_ok() PASSES having run no guards at all.
 [V] Mechanism: require_ok() raises only when status["flags"] is non-empty, and a check that
     never ran contributes no flag.

 3.2  CHECK STATUS  [I]
 Status describes ONE check.  It says nothing about acceptance.

     PASSED          ran; the model met it
     FAILED          ran; the model did not meet it
     SKIPPED         this engine can compute it here; it was not run (diagnostics=False, budget)
     UNSUPPORTED     this engine cannot compute it
     NOT_APPLICABLE  the check has no meaning for this model
     MISSING         applicable and supported, was to run, produced no record -- a package defect

 [I] NOT_APPLICABLE is a property of the MODEL (a lag-window guard on a finite horizon).
     UNSUPPORTED is a property of the ENGINE (representation error on the cell engine).
     The two are never merged: one means nothing is missing, the other means something is.

 3.3  EXPECTED INVENTORY  [I]
 [I] The checks that APPLY are computed from the model and the policy, independently of the rows
     an engine emits.  An applicable check with no emitted row is never simply absent -- but it is
     not automatically UNSUPPORTED either.  CAPABILITY IS DETERMINED FIRST, and the three reasons
     are kept apart:

         applicable, engine cannot compute it            -> UNSUPPORTED
         applicable, engine can, deliberately not run    -> SKIPPED   (diagnostics=False, budget)
         applicable, engine can, was to run, no record   -> MISSING

     MISSING is a defect in this package, not a property of the model or the engine, and is
     reported as such.  Draft 2 called every absent record UNSUPPORTED, which mislabels a solve
     run with the guards off as an engine limitation.
 [V] Without this, the cell engine's missing second_order row disappears from evaluation
     entirely rather than being reported as missing (3.1).

     applicable_checks(model, policy) -> frozenset[str]      [I]  from model + policy only
     supported_checks(engine)         -> frozenset[str]      [I]  engine capability
     an applicable check not in supported_checks is UNSUPPORTED, always, on every run.

 3.4  VALIDATION POLICY  [I]
 [I] D2 RESOLVED: the policy is a first-class object.

     class Policy:
         name: str
         required: frozenset[str]          # by check root, e.g. "second_order"
         def applies(self, model) -> frozenset[str]

     Policy.PUBLICATION   required = {converged, resolution, window, second_order, settled}
     Policy.EXPLORATORY   required = {converged}

 [I] D3/D5 RESOLVED, and they were never independent questions.  Requirements follow the POLICY
     and the MODEL.  Engine capability decides whether a requirement can be SATISFIED, never
     whether it applies.  There is NO automatic engine exemption.
 [I] Draft 1 said the default policy requires checks "where the engine defines them".  That
     phrase reintroduced the exemption it claimed to close, and is removed.
 [I] A weaker requirement set is legitimate and must be a DIFFERENT NAMED POLICY.  Consequence,
     stated plainly: under PUBLICATION the cell engine cannot produce an accepted result, because
     it cannot compute two required checks.  That is the honest report, not a defect to route
     around.

 3.5  AGGREGATE CONTRACT  [I]
 [I] The six statuses describe individual checks and do NOT describe a collection.  An
     aggregate returns a structured assessment, never a single status.

     @dataclass(frozen=True)
     class Assessment:
         accepted: bool                        # every required, applicable check PASSED
         policy: str
         blocking: tuple[Blocker, ...]         # empty iff accepted
         statuses: Mapping[str, Status]        # every applicable check, by name
         uncomputed: tuple[str, ...]           # applicable, produced no result, for ANY reason:
                                               # UNSUPPORTED, SKIPPED or MISSING

     @dataclass(frozen=True)
     class Blocker:
         check: str
         status: Status                        # FAILED, SKIPPED, UNSUPPORTED or MISSING
         reason: str

 [I] `uncomputed` is the FIELD listing every applicable check with no result, whatever the reason.
     MISSING is one STATUS a check in that list may carry.  Draft 2 called the field `missing`,
     which collided with the status name and read as though the field held only that case.

 [I] EMPTY IS NOT THE SAME AS MISSING, and acceptance is decided only after the expected
     inventory of 3.3 has been consulted:

         no APPLICABLE check           accepted=True, statuses={}, blocking=(), uncomputed=()
                                       Nothing was required here.  Emptiness is visible in
                                       statuses rather than reported as a pass.
         applicable checks, no records Each such check takes UNSUPPORTED, SKIPPED or MISSING
                                       per 3.3 and appears in `uncomputed`.  accepted=False ONLY IF
                                       one of them is REQUIRED by the policy.  An OPTIONAL check
                                       with no record is reported and does not block -- Draft 2
                                       said no-records always means rejection, contradicting its
                                       own acceptance table.

     An assessment must never read an absent record as an empty category.  That is the cell
     engine's missing second_order row (3.1), and it is the whole reason 3.3 computes the
     inventory from the model and policy rather than from what an engine emitted.

 3.6  ACCEPTANCE TABLE  [I]

     status of a check       required by policy      optional
     -------------------------------------------------------------------
     PASSED                  does not block          does not block
     FAILED                  BLOCKS                  reported, no block
     SKIPPED                 BLOCKS                  reported, no block
     UNSUPPORTED             BLOCKS                  reported, no block
     NOT_APPLICABLE          does not block          does not block

 [I] MISSING blocks exactly as UNSUPPORTED and SKIPPED do: required blocks, optional reports.
 [I] ACCEPTANCE, stated once and without exception: accepted is True iff every check that the
     policy REQUIRES and the model makes APPLICABLE has status PASSED.  Nothing else grants
     acceptance -- not an absent record, not an empty category, not an engine limitation.
 [I] Every non-PASSED status appears in `statuses` whether or not it blocks.  Optional failures
     are never silent.

 3.7  SIGNATURES  [I]

     res.diagnostics                                        -> Diagnostics
     Diagnostics.rows                                       -> tuple[CheckRow, ...]
     Diagnostics.statuses                                   -> Mapping[str, Status]
     Diagnostics.assess(policy: Policy = Policy.PUBLICATION) -> Assessment
     Diagnostics.summary(detailed: bool = False)            -> str
     Diagnostics.by_category(category: str)                 -> tuple[CheckRow, ...]

     res.require_ok(policy: Policy = Policy.PUBLICATION)    -> Result   (raises)
     res.require_converged()                                -> Result   (raises)

 [I] EXCEPTIONS.  The two failures are SIBLINGS, not parent and child:

         ResultValidationError            a result is not fit for the use asked of it
         |-- ConvergenceError             the solve did not reach its tolerance
         |-- DiagnosticsError             it converged, and the assessment was not accepted

     A converged result can fail diagnostics, so DiagnosticsError must NOT be a ConvergenceError:
     `except ConvergenceError` would then catch failures that have nothing to do with convergence.
     A caller wanting either writes `except ResultValidationError`.
 [I] require_ok() succeeds iff assess(policy).accepted.  When it does not, WHICH exception is
     raised follows the reason, so each exception's contract stays true:

         the `converged` check did not pass   -> ConvergenceError
         anything else blocked                -> DiagnosticsError

     Both carry the Assessment.  Convergence is still an ordinary check inside the policy; this
     rule only decides which name the failure is reported under, so that DiagnosticsError can
     continue to mean "it converged, and was still not accepted".  Draft 2 raised DiagnosticsError
     for every rejection, including non-convergence, which contradicted its own contract.
 [I] The message distinguishes "failed" from "could not be established", which call for different
     actions from the reader.
 [I] require_converged() is unchanged, tests the solve only, and raises ConvergenceError.
 [I] Replaces, and removes: diagnostic_rows, diagnostic_records, diagnostic_summary,
     diagnostic_verdict, status, resolution_ok.
 [I] A check name's ROOT is the part before any ":".  Category and exclusion both key on the root,
     so "second_order" covers "second_order:<agent>".
 [V] Matching the full name instead silently excluded nothing (fixed 2026-09-09, tested).

 PART 4   STABILITY
================================================================================================

 4.1  WHAT IS WRONG
 [V] compare() calls result.stability() with no guard between it and solve(), so a scenario that
     never converged still receives a response classification.  ScenarioResult.dynamics omits the
     fixed_point_residual that stability() computes.

 4.2  A CORRECTION TO DRAFT 1
 Draft 1 wrote, under a [V] marker, that two observations showed a converged solve need not be an
 equilibrium: a fixed point costing seven times another, and a case where the second-order check
 passes while the best-response radius exceeds 1.  Neither supports that conclusion.

     - Distinct equilibria may have distinct costs.  A higher cost is not disqualifying.
     - An equilibrium may be unstable under best-response iteration.  rho > 1 is a statement
       about the dynamics, not about validity.

 [V] The numbers were verified; the inference was not, and is withdrawn.  The observations are
     kept as observations.

 [V] What the ch3 long-window case does show: a stationary window much longer than the kernel's
     support admits a second fixed point of the TRUNCATED problem, and on that branch the kernel
     has not decayed by the window's edge, so the window guard fails.
 [I] The correct reading of that guard, and no more: a failed window guard establishes that the
     TRUNCATION IS NOT VALIDATED -- the truncated problem's fixed point has not been shown to be a
     fixed point of the untruncated one.  It does not by itself prove the branch is an artifact.
     Draft 2 said the guard "makes it an artifact", which is a stronger claim than insufficient
     evidence supports.  What follows is that the branch is UNVERIFIED, which is exactly the
     verdict 4.3 is built to express.
 [I] EQUILIBRIUM VALIDITY AND RESPONSE STABILITY ARE SEPARATE FINDINGS and are reported
     separately.  Neither is evidence for the other.

 4.3  SIGNATURE AND RETURN  [I]

     @dataclass(frozen=True)
     class Stability:
         radius: float
         eigenvalues: tuple[complex, ...]
         method: str
         fixed_point_residual: float
         residual_norm: str                 # which norm, and its scaling
         residual_tolerance: float | None    # None until D4 is settled
         verified: bool                     # a real bool, per R3
         unverified_reasons: tuple[str, ...]   # empty iff verified
         full_response: str | None
         adjusted_response: str | None
         adjusted_radius_bound: float | None
         adjustment: float

     res.stability(untied: bool = True, policy: Policy = Policy.PUBLICATION) -> Stability

 [I] The classification fields are ALWAYS PRESENT, and are None when verified is False.  Draft 1
     removed them conditionally; that makes attribute access depend on the data, which is worse
     than a documented None.
 [I] THE VERIFICATION RULE, stated as the computation rather than as prose:

         MINIMUM  = {converged, resolution, second_order, window}
         required = applicable(MINIMUM | policy.required, model)
         verified = residual_passed and all(statuses[c] is PASSED for c in required)

     The UNION is what makes both halves true at once, and prose got each of them wrong once:
       - a WEAK policy cannot lower the bar, because MINIMUM is always in the union.  It also does
         not by itself cause rejection: if every applicable check in the union passed, verified
         is True under Policy.EXPLORATORY.  That is NOT equivalence with Policy.PUBLICATION,
         which contributes `settled` to the union and so has more to satisfy; a weak policy
         simply adds nothing beyond MINIMUM.  Draft 2 rev 2 said a policy too weak to satisfy
         the minimum yields verified=False, which wrongly made the policy the cause.
       - a STRONG policy's ADDITIONAL required checks must also pass.  Draft 2 rev 2's "iff"
         named only the minimum, so a stronger policy's extra checks did not bind.
 [I] APPLICABILITY IS COMPUTED FROM THE MODEL, never hard-coded per kind.  `window` in particular
     is applicable wherever the model carries a lag-truncation window, which is a stationary model
     AND a transition (whose continuation carries one -- PART 2).  It is not applicable to a plain
     finite horizon.  Draft 2 rev 2 wrote "window where the model is stationary", which silently
     dropped transitions from verification.
 [I] residual_passed is fixed_point_residual <= residual_tolerance under residual_norm, and is
     False whenever residual_tolerance is None (D4 unsettled).
 [I] unverified_reasons names every element of `required` whose status is not PASSED, and the
     residual condition when it is the one that failed.
 [I] Reading the set from the policy alone -- Draft 2's rule -- would let Policy.EXPLORATORY
     produce verified=True on weaker evidence under the same label.  That is the engine-exemption
     loophole of 3.4 returning by another route; the label must mean one thing.
 [I] The Jacobian at a non-fixed point remains computable: radius, eigenvalues, method and the
     residual are always returned.  Only the INTERPRETATION is withheld.
 [I] D4 DOES NOT BLOCK THE REST OF THIS SPECIFICATION.  The three report fields --
     fixed_point_residual, residual_norm, residual_tolerance -- are specified and populated from
     the start, so the evidence is carried and serialised even before the numerical definition is
     settled.  What is gated is only the CLASSIFICATION:

         until D4 is settled   residual_norm names the norm actually used; residual_tolerance is
                               None; verified is False; unverified_reasons contains
                               "equilibrium residual criterion not yet defined"; the three
                               classification fields are None.
         after D4              verified is computed as in 4.3 and the classification appears.

     A caller therefore never sees a classification resting on an undefined criterion, and never
     has to guess whether one is missing because the point failed or because the criterion does
     not exist yet.
 [O] D4  The numerical definition: the NORM, its SCALING, and the threshold, specified together so
         the number is comparable across grids and model scales.  The solve residual is not, which
         is why it cannot serve.  This is numerical work, not API work.

 PART 8   SIGNALS, WARM STARTS, READING FILES

 8.1  SIGNALS  [I]

     @overload
     Model.with_signal(signal: Signal, *, audience: str | Sequence[str] = "all") -> Model
     @overload
     Model.with_signal(name: str, *, drift: Mapping[str, float], noise: Mapping[str, float],
                       audience: str | Sequence[str] = "all", delay: float = 0.0) -> Model
     @overload
     Model.with_signals(signals: Sequence[Signal], *, audience = "all") -> Model
     @overload
     Model.with_signals(rows: Mapping[str, dict], *, audience = "all") -> Model

     BOTH OVERLOADS ARE PART OF THE CONTRACT.  This was implemented from the first line alone,
     which rejected a positional name and broke every existing caller.  The failure was not that a
     signature block cannot express two calling shapes -- typing.overload does, and both were
     already written here, adjacent -- it was reading one of them.

 [I] Both forms are retained and overloaded on the first argument: a Signal, or a name plus the
     file-form blocks.  The dict form exists because a model loaded from a file has no Signal
     object to hand.  Mixing forms in one call is an error.
 [I] DUPLICATE NAMES: adding a row whose name an agent in the audience already has is an error
     naming the agent and the row.  It is never a silent replacement.  To replace, the caller
     removes first -- Model.without_signal(name, audience="all") -> Model.
 [I] Noise channels named by a new row are appended to model.channels in the order given, and
     only if not already present.

 8.2  WARM STARTS  [I]
 [V] init and start are not duplicates: init is an object (action kernels or raw maps); start is
     a strategy name ("zero", "coarse", "stationary").

     ns.solve(..., start_from: Mapping[str, ndarray] | None = None,
                   start_policy: str | None = None, ...)

 [I] D8 RESOLVED on the names.  THEIR INTERACTION: supplying both is an ERROR, not a precedence
     rule.  A precedence rule silently discards one of two things the caller asked for, and the
     caller cannot tell which was used.  The error names both arguments.
 [I] start_policy=None with start_from=None means the engine's default, which each engine names
     in its documentation.

 8.3  READING FILES

 [V] The duplication is internal: sweep._load_dict reimplements as_model over the same four-way
     union with the TypeError message copied verbatim.
 [I] sweep._load_dict is removed; as_model is the one normalizer.

 PART 10   CONTRACTS TO BE TESTED
================================================================================================

 Derived from P1 and the rules; each is decidable.

 INVESTIGATIONS -- open questions that block nothing

 I1  CROSS-REGIME DELAYED OBSERVATIONS.  A transition refuses a row delayed beyond T, on the
     grounds that it "carries nothing within the window".  That reason is not right for a
     transition: the past is solved and attached, and the grid represents it -- a transition
     result's shock_time axis was measured running from -3.0 with T = 1.0 (2026-09-10).

     What that measurement establishes is only that PAST SHOCKS ARE REPRESENTED.  It does NOT
     establish that a delayed observation crossing the regime boundary is resolved correctly, which
     depends on the signal definitions, on what each agent knows on either side, and on how the old
     and new regimes join.  Nor does it justify substituting the past's extent as the validation
     bound.

     The restriction is kept and the message now says what it is: a limit of the current engines,
     not a claim that the model is ill-posed.  Lifting it requires establishing the semantics
     first, and then testing that the engines deliver them.
